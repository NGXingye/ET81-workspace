# 0. 速览

> 速览：本机工具代码（SkillPipeline、SkillSync、Bridge 本地编辑器工具）的拆 / 合 / 不动判断、注释与文件职责。阈值都是软参考。
> 最大风险：在原大函数上一直打补丁越写越巨石；或反过来拆成一堆转手的小文件。
> 做对的标准：改到的每个文件职责一句话说得清；`plan` 对碰到的大文件或小文件写明拆、合或不动及理由。
>
> 门禁：无单独门禁，可写范围按当前任务的 `write_paths`。

# 1. 怎么运转

- 原则：改到哪、整理到哪。只处理本次 `write_paths` 里的文件，不顺手重构无关部分，不单独开大重构。
- 步骤：先挪后改。纯移动、行为不变、编译通过后再加新功能。拆出的新文件按补活卡进 `write_paths`（须用户同意）；落在 profile 前缀外才要放宽 profile（须用户同意）。
- 粒度：一件事一个文件，拆出文件宜 300–1000 行，避免碎片。优先 partial 类按职责分文件，对外接口不变；新功能优先放新文件，沿用现有命名。
- 定位：对应模块卡「怎么运转」维护简短的文件职责表（一文件一行），拆合后由 `/harvest` 补。Bridge `SkillPipelineBridge*` partial 职责表写在 `skill_sync.md`（Author/Shots/Phase/Boxes/Launch）；新 partial 同单进 `local_only` + `etctl sync-ignores`。

# 2. 坑和不变量

- 拆的信号（满足两条以上）：约 1200 行以上且仍在增长；混着两件以上不相干的事；改一个功能要在同文件多处不相关位置来回改；几乎每次需求都改它。
- 合的信号（一条即可考虑）：约 150 行以下且只有一处调用；几个小文件总是一起改；只是转手的壳。
- 不动：大但职责单一、很少改；本次没碰到。
- 注释：文件头 3–5 行（负责什么、不负责什么、上下游）；方法内只写「为什么」，不写「做了什么」；坑类注释可指向 `standards/` 卡片，不重复长篇；不要求每个方法都写。改到的无头注释文件顺手补头注释。
- 新建本地工具文件同单补进对应 `targets/<id>.json` 的 `local_only`，再跑 `etctl sync-ignores`（见 `skill_sync.md`），否则会被当成待提交文件。

# 3. 怎么验证

- 先挪那一步单独编译通过、行为不变，再加功能。
- 新文件有头注释；模块卡文件职责表与磁盘一致。
